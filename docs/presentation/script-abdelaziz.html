Slide 8 Two applications, one database

"Thank you Malik. The system is two applications sharing one database."

"The part people see is built with Next.js and React — the driver's app, the operator's app and the manager's dashboards. Behind it is a back end with fifty-three endpoints, and that is where every business rule lives. The screens never touch the database directly. That matters because it means a rule cannot be enforced in one screen and forgotten in another."

"Underneath is MongoDB with fourteen collections. And one thing worth pointing out — we keep a history of everything that happens to a booking, and that history is only ever added to. It is never edited. Scores and reports are calculated from it rather than stored."

Slide 9 The one rule the database enforces — your key slide

"This is the most important technical decision we made, so I want to spend a moment on it."

"We split charger time into fifteen-minute blocks. A booking from three to four o'clock owns four of those blocks. And we told the database: one block can be owned by only one booking, ever."

Point at the diagram: "So when Ben tries to book three-thirty to four-thirty, he needs two blocks Anna already owns. The database refuses it. Not our code — the database itself. But when Ben books four o'clock to five, nobody owns those blocks, so it works. Two bookings sit back to back with no time wasted between them."

Say why: "We could have written this check in our own code. We started that way. The problem is that a check in code can be skipped by a feature somebody writes later, and if two requests arrive at exactly the same moment they can both pass it. A rule inside the database cannot be bypassed by code that does not exist yet."

If a mentor pushes: MongoDB has no built-in way to say "these two time ranges must not overlap". Splitting into fixed blocks turns overlap into a simple duplicate-key rule, which the database does enforce natively. The cost is that bookings start on the quarter hour. We accepted that trade deliberately.

Slide 10 · Built to survive its own failures 0:40 · new — cannot be filmed

Why this slide exists: none of these four can appear in any video. You would have to crash the system, corrupt a projection or send a duplicate message on purpose to show them. Say that out loud — it is the point of the slide, not an excuse.

"Four decisions you will not see in any of our videos, because each one only shows itself when something goes wrong."

Take two of the four, not all: "We write the booking first and claim the time second. So if the system dies half way, we are left with a booking holding nothing — which our repair tool finds and reports. The other order would leave time held by nothing: invisible to every query, bookable by nobody, and impossible to notice. We chose which way it breaks."

"And every message carries a key the database refuses to duplicate. Run the message worker twice and you get zero new messages, not two copies of everything."

The closing line: "None of that is demonstrable without deliberately breaking our own system — which is exactly why it is worth telling you about."

Slide 29 · Design lessons 1:15

"Three lessons from the design side."

"First — preventing double bookings belongs in the database, not in our code. We tried it in the application first. A check in code can be skipped by a feature written later, and two requests arriving together can both pass it. Moving it into a database rule made it impossible to break."

"Second — we had to model charger time as small blocks. We started with fixed thirty-minute slots, but real charging is anywhere from fifteen minutes to two hours. Splitting time into fifteen-minute blocks let us support any length with one simple rule. And we got the boundary wrong once, in a way that made every back-to-back booking impossible — which taught us to test the edges, not the middle."

"Third — scores have to be rebuilt from history, never counted up as you go. A running total drifts. If one update is missed or repeated, the number is wrong forever and nobody can tell. Recalculating from the recorded history means a repeated event cannot double-count and a lost one repairs itself."

Hand over → "Malik has the three that surprised us most."

Questions likely to come to you Q&A

QuestionShort answer
Why MongoDB and not SQL?Honest answer: it is what the team knew. A relational database with an exclusion constraint would express the overlap rule more directly. We got the same guarantee by splitting time into blocks and using a unique index.
Why fifteen minutes?It divides evenly into every length we support — 15, 30, 45, 60, 90 and 120. No rounding and no wasted time. One minute would multiply the number of database writes by fifteen for precision nothing needs.
What if two people click at exactly the same millisecond?One of them gets a duplicate-key error from the database and is told the charger is busy. This is tested — it is one of our automatic checks.
How do you know the station scoping works?We tested it by running it: the assigned station is allowed, an unassigned one is refused with a 403, and an admin bypasses it by design. We can show that.
Is the QR code secure?It contains only the booking code, which the operator could also type. It is a lookup shortcut, not a credential — and the operator still has to be logged in and assigned to that station.
Are the payments real?No. They are simulated, and no card data of any kind is accepted, stored or displayed. What is real is the rules and the records — every deposit, refund and forfeiture is written down with its reason.
How hard would real payments be?The connection point already exists, along with the payment-intent and refund records and the protection against charging twice. It is a swap, not a rebuild.
Could a driver claim it was your fault to get a refund?No. Only staff or an admin can set the operator-fault flag, and that is checked on the server.
