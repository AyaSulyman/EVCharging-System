The contested afternoon

Two drivers want one charger — and the system decides, then explains itself.

ChargeHub — Downtown
Window 1 · driver A
demo.reliable@chargehub.comDemo123! · Rami, score 100
Window 2 · driver B
demo.typical@chargehub.comDemo123! · Lina Aoun, score 56
Window 3 · manager

Run this before you record, or the counterfactual proves nothing. 
cd backend
npx tsx scripts/setup-contention-demo.ts
The comparison only differs when capacity is genuinely scarce. With a few requests and ten mostly-free chargers, a queue serves exactly the same people as the optimizer and the number honestly says so — measured at 2 vs 2, which proves nothing on camera. This script fills Downtown's afternoon nine days out, leaves one free hour, and submits three flexible requests plus one that can only be served in that hour. Verified on your database twice: 6 vs 5, then 5 vs 4 after part of the pool had been consumed. The gap is the point, not the absolute numbers. Clear it after recording with the same command plus --clear — it deliberately makes a station look full.
Order matters, and getting it wrong silently kills the comparison. "Preview a pass" measures the pool as it stands right now. "Run and issue offers" consumes requests out of that pool by offering them a charger. So:

1. Run the setup script  →  2. record the Preview beat while the pool is full  →  3. only then press "Run and issue offers" for the offer beat.

Commit first and the pool shrinks, so a later Preview shows a smaller gap or none at all — which is exactly how this reads "2 vs 2" again. If that happens, re-run the setup script and record the Preview beat before committing anything.
Why these two drivers. Rami scores 100 and Lina 56 — an ordinary driver with a few late arrivals, not a disaster. That gap is visible in the score table: Lina’s options carry a "value discounted to 60%" line and Rami’s do not, because the discount is floored at 60% no matter how low a score goes. Check both scores on /admin/reliability before you record; regenerating demo data reshuffles them.

Record these actions — silently

  1. Window 1From Stations → Downtown, press Book on a charger — that link carries the charger, so it opens the step-by-step wizard at /book/exact. Take 15:00–16:00, 60 minutes, pay the deposit, stop on the QR screen.
    "This is Rami. He knows exactly when he needs to charge, so he picks his own time. Watch the available start times as I change the length — that is not a stored list of slots, it is worked out from what is genuinely free right now."
    0:18 — "Not a stored list. Calculated from what is actually free, for this exact length."
  2. Window 2Try to book the same charger, the same hour. Let it fail. Hold for 3 seconds.
    "Now Lina wants the same charger at the same time. And she is refused — but notice who refused her. Not our code. The database itself. We split charger time into fifteen-minute blocks and told the database one block can have only one owner, ever. A rule that lives inside the database cannot be bypassed by a feature somebody writes next year."
    0:42 — "Refused by the database, not by our code."
  3. Window 2Book 16:00–17:00 instead. It succeeds.
    "But sixteen hundred works. A booking that ends at four o'clock does not own the four o'clock block — so these two sit back to back with not one minute wasted between them. We got that boundary backwards once, and it made every adjacent pair unbookable. It is now an automatic test."
    0:58 — "15:00 · 15:15 · 15:30 · 15:45 owned — 16:00 free."
  4. Window 2Cancel that booking. Then press Book now in the navbar — it goes straight to the booking form. Ask for about 30 minutes, any time this afternoon, Downtown. Leave "Hold the best match for me automatically" switched OFF, and when the shortlist appears do not take any of them.
    "Now the interesting half. Instead of naming a time, she describes a window — about thirty minutes, some time this afternoon. That is the whole difference. A step-by-step wizard can only answer 'which of these exact times?' It has nothing to say when the honest answer is none of them."
  5. Window 3Open /admin/optimizer. Show the demand pool. Hold 4 seconds.
    "Here is everyone currently waiting. And this is the part I most want you to see — the system is not answering one person. It is planning all of them against the same chargers at the same time. If you score people one at a time, two of them will happily be handed the same charger."
    1:30 — "Not answering one person. Planning all of them against the same chargers at once."
  6. Window 3Go to /admin/optimizer. Press "Preview a pass" — the left of the two buttons, top right of the page. An amber card appears headed "Preview — nothing was held".
    Use Preview, not "Run and issue offers", for this beat. Preview runs the identical code path and holds no capacity, so you can press it as many times as you like while recording without freezing a bay. You will press the other button later, when you actually want the offer.
    "One pass, planning everyone at once. Milliseconds — and it has a hard time limit, because a booking screen must never be left waiting on the optimizer."
  7. Window 2On the results list, each option has a small "Why this score?" link under its reasons. Click it on the top option — the one tagged Best match. A table opens underneath it.
    What this table is, so you can narrate it confidently. The system does not guess an order. It gives every possible option a number, and the option with the highest number goes to the top. This table is that arithmetic, made visible — five rows, one per factor, each with a signed number (green if it helped, red if it cost), a short reason, and a bold Total at the bottom.

    The rows are labelled Your preferences · Station capacity · Time waiting · Priority · Attendance record. Above the whole list there is also a one-line summary next to a sparkle icon — that is the plain-English version of the same decision.

    The row to point at: the Total line. For Lina it ends with "value discounted to 60%". That is her attendance record shrinking the value of the slot — and it is the only place in the product where reliability is visible doing its job. Rami’s table has no such line, because a perfect record discounts nothing. Show one, then the other.
    "And every option comes with its reasoning — not a marketing sentence, the actual arithmetic. Five things, each worth points. Does this keep the free time in usable blocks. How close is it to the time she asked for. How long has she been waiting. Is she standing at a desk or recovering from a fault that was ours. And how likely is she to turn up."
    "Look at the bottom line. Her attendance record has discounted the value of this slot to sixty percent — that is reliability, doing the only thing it is allowed to do: break a tie. It never blocks her from booking. And on the driver with a perfect record, that line simply is not there."
    "This is not a debug screen we built for ourselves. It is what the customer sees. So when somebody asks why they were given four-thirty instead of three, there is a real answer and not a shrug."
    1:52 — "Every option shows its own arithmetic. Five factors, signed points, a total."
    2:05 — "'Value discounted to 60%' — that is the attendance record breaking a tie."
    2:14 — "This is the customer's own screen, not a debug view."
  8. Window 3Still on /admin/optimizer. The comparison is in two places — show both. Hold 5 seconds on the first.
    1. The amber Preview card, just under the page heading. It reads, in one sentence: "6 requests would be offered a charger. First-come-first-served would have served 5. Planned in 378 ms." (Numbers verified on your data with the setup script above.) That single line carries the whole argument — and the milliseconds are the proof of the time bound you mention on slide 33. Zoom in on it when you edit.

    2. The "Run history" table, lower down the same page. Compare the "Offered" column against the "FCFS would serve" column, row by row. The table's own subtitle says why it exists: "'Served' against 'FCFS' is the optimizer's whole claim, measured on the same snapshot each pass ran against." Scroll so a few rows are visible — one row is an anecdote, several are a pattern.

    If the table is empty it says "No passes have run yet". Press "Preview a pass" once more; previews are recorded too.
    "And we do not just claim this helps. Every single run also works out what plain first-come-first-served would have achieved on exactly the same data, and stores both numbers. Six against five here — one more customer served from the same chargers."
    2:15 — "Same chargers, same moment. A queue serves 5. This plan serves 6."
    "And when there is plenty of capacity free, these two numbers come out equal — because no scheduler can beat a queue when nobody has to be turned away. That is worth saying: the comparison is built to tell us when we are not adding anything."
  9. Window 3Back on /admin/optimizer, now press the second button — "Run and issue offers". This is the one that commits, and it issues a real held offer to Lina's still-open request.
    This step is what makes the next one work. Nothing you did earlier creates an offer: "Preview a pass" deliberately holds nothing, and submitting the request only produced a shortlist for her to choose from. Without pressing "Run and issue offers" here, /offers is empty and there is nothing to accept. That is also why beat 4 said to leave the shortlist alone — taking a candidate would have fulfilled the request, and a fulfilled request gets no offer.

    The alternative, if you prefer fewer windows: on the booking form, switch "Hold the best match for me automatically" ON. Then the optimizer chooses and holds one at submission time and sends her straight to /offers — no admin step at all. It is the shorter path, but you lose the shortlist, and with it the "Why this score?" table from beat 7. Use the admin route if you want both.
  10. Window 2Open /offers. The offer card shows a m:ss countdown from 5:00, with a shrinking bar; under a minute left it turns urgent. Press Accept. You land on /bookings with the booking marked PENDING_PAYMENT. Pay the deposit there to finish.
    Do not linger. The hold really is five minutes. If it lapses mid-take the card expires and you will need another pass. Record this beat promptly after issuing the offer.

    The seconds come from the server on every poll, not from a clock in the page — which is the claim you are about to make, so it is worth knowing it is literally true.
    Do not stop at Accept. Accepting converts the hold into a booking in PENDING_PAYMENT — the app itself says "Charger reserved — pay the deposit to confirm it" and sends you to /bookings. Unpaid, it is released automatically when the ten-minute window closes. If you end the recording at Accept you are showing a booking that is about to disappear.
    "She is offered a slot, and that charger is genuinely held for her — nobody else can book it for five minutes. That is what makes pressing accept safe: the charger was already secured when the offer was made, so accepting cannot fail. And the countdown comes from our server, not from her phone, so a device with the wrong clock cannot show an expired hold as still valid."
    "Accepting turns the hold into a real booking — and then she still has to pay the deposit to confirm it. Two different clocks, and they do different jobs. Five minutes to decide, because a held charger is frozen stock and an ignored offer costs somebody else a bay. Then ten minutes to pay, because a booking nobody has committed to is not a booking. Miss either one and the charger goes straight back on sale."
    2:40 — "Genuinely held. Nobody else can book it for five minutes — so Accept cannot fail."
    2:52 — "Two clocks: 5 minutes to decide · 10 minutes to pay. Miss either and the bay returns to sale."
This scenario proves
One block one owner (database-enforced) · half-open boundaries so back-to-back works · availability computed per requested duration · deposit confirms a booking · flexible windows · multi-request planning · five-factor scoring with stored reasoning · determinism · the first-come-first-served counterfactual · offers holding real capacity · server-trusted countdown · reliability changing an outcome between a 100 and a 79.

Record these actions — silently

  1. Window 1Press Book now, choose Airport, a window later today. Pay the deposit. Show the QR code.
    "Sara books a charger at the airport and pays a small deposit. I should say this before anyone asks — the payment is simulated. No card number, expiry or security code is ever entered, stored or shown anywhere in this system. There is no field for one. What is real is the rules and the records."
    0:20 — "Payment simulated. No card data is accepted, stored or displayed anywhere."
  2. Window 2On /staff, use the Scan QR card and type the booking code into the manual field rather than using the camera. Press Check in.
    Read the outcome off the screen — do not name it in advance. The arrival is classified against the clock: booking ahead and checking in now gives EARLY, not ON_TIME. ON_TIME means arrival at exactly the scheduled minute, which you will not hit on cue. Say whichever label appears; the point is that nobody typed it.
    "On the station side I look her up. I can scan the code on her phone with the camera or type it by hand — both go through exactly the same lookup, so nothing is different. And the moment I check her in, the system has already classified the arrival — early, on time, inside the grace period, late, or a no-show. It says early here, because she turned up ahead of her slot. Nobody typed that in; it is worked out from the booking and the clock, and it is what the reliability score is later built from."
    0:48 — "Classified automatically against the clock. Nobody types this."
  3. Window 2Start the charging session.
    "Starting and ending are two separate recorded steps, which means we always know how long the bay was really used — not just how long it was booked for. That is the difference between a utilisation figure that reflects reality and one that reflects intentions."
  4. Window 2Go to /staff/incidents and report a charger failure on a different Airport charger that has bookings behind it.
    "Now something goes wrong. A charger fails, and I report it. It goes unavailable immediately — nothing new can be booked onto it from this second."
    1:20 — "Charger unavailable immediately. Nothing new can land on it."
  5. Window 2Open the delay cascade panel. Hold 5 seconds.
    "The system works out which bookings are affected and walks the delay forward — this one, then the one queued behind it, then the one behind that. And here is the part I care most about. It has not cancelled anything. It computed the delay, worked out who is affected, and stopped. A person decides. We felt that cancelling somebody's booking should be a human decision, not something a background job does quietly at four in the morning."
    1:40 — "It has NOT cancelled anything. It computed, identified, and stopped. A person decides."
  6. Window 2Cancel one affected booking, marking it operator fault. Show the full refund.
    "When I cancel because of our fault, that driver is refunded in full — even inside the twenty-four hour window where normally the deposit is kept. Our fault always beats the clock. And only staff or an admin can set that flag, checked on the server. If a driver could mark their own cancellation as our fault, they would refund themselves every single time."
    2:05 — "Refunded inside the 24-hour window. Our fault beats the clock."
  7. Window 3Show that driver's reliability score — unchanged.
    "And their score is untouched. Fault is stamped onto the event at the moment the decision is made, so a scorer reading the history later can never accidentally punish a driver because our charger broke."
    2:20 — "Reliability untouched. Fault is stamped as it happens."
  8. Window 2Try to act on a Downtown charger. Show the refusal.
    "Last thing. I am assigned to the airport, so when I try to act on Downtown the server refuses me. Not a hidden menu — an actual permission check, on the server, on every action."
    2:40 — "403. This operator is assigned to Airport. Refused by the server, not hidden in the menu."
This scenario proves
Deposit confirms a booking, no card data anywhere · QR and typed code share one lookup · arrival classified automatically · start and end recorded separately · incident lifecycle separate from reservation state · affected chargers unavailable at once · delay walked forward through the queue · recommended, never applied · operator-fault waiver beats the refund cliff · fault stamped at decision time so reliability is protected · station scope enforced server-side.

Station
ChargeHub — Marina
Window 1 · driver A
demo.typical@chargehub.comDemo123! · Lina — leaves early
Window 2 · driver B
demo.slipping@chargehub.comDemo123! · Ziad — gets waitlisted
Window 3 · operator
staff.marina@chargehub.comStaff123! · Fadi, Marina only

Record these actions — silently

  1. Window 1Press Book now, choose Marina, 60 minutes, a narrow window starting shortly.
    "Lina books an hour at the marina this afternoon."
  2. Window 2Press Book now and ask for the same window at Marina, now that it is full. Land on the waitlist.
    "Ziad wants roughly the same time, and there is nothing free. In most systems that is where he disappears — 'sorry, fully booked', and you have lost the customer. Here he keeps his place and the request stays alive. A waitlist entry in our system is not a separate list; it is simply a request we have not been able to satisfy yet, and it gets reconsidered automatically every single time a charger frees up."
    0:30 — "Not turned away. The request stays live and is reconsidered on every release."
  3. Window 3On /staff, find Lina's booking: Check in → Start charging → End charging. Do all three back to back; you do not wait.
    No waiting required. Check-in is gated on the booking's state, not on the clock, so you can run the whole session immediately after paying the deposit. Ending it early releases everything between now and the booked end — so a 60-minute booking ended straight away returns close to the full hour. Read the released figure off the screen rather than scripting a number.
    "She arrives, starts charging, and then finishes early — which is the ordinary thing that happens every day and that almost no system does anything about."
  4. Show the freed capacity. Hold 3 seconds.
    "Those unused minutes have just gone back on sale. In most systems that time is simply lost, because nobody knows it became free. Here it is recorded as capacity released, with the reason attached, and the minutes are counted — so recovered capacity is something we measure rather than something we claim."
    1:00 — "Unused minutes back on sale. Recorded as EARLY_DEPARTURE — and counted."
  5. Show the workers terminal for 8 seconds, then hard cut.
    "These background workers run every minute. Nobody clicks them — time is what triggers this, not a person."
    1:15 — "60 seconds later."
  6. Window 2Open /offers, press Accept, land on /bookings, then pay the deposit on the PENDING_PAYMENT booking.
    Accepting is not the end of the story. It creates the booking in PENDING_PAYMENT and redirects to /bookings; the deposit is paid there. Stop at Accept and you have filmed a booking that expires in ten minutes — which contradicts the line you are about to say.
    "And within a minute Ziad is offered that exact slot. He accepts, pays the deposit, and it is his. Nobody at the station phoned anyone. Nobody reassigned anything by hand. A customer who would have been turned away half an hour ago is now a customer we served — out of time that would otherwise have been thrown away entirely."
    1:35 — "Turned-away demand became served demand. No human involved."
    1:48 — "Accepted, then confirmed with a deposit. An unpaid booking returns to sale in 10 minutes."
  7. Window 1Open the bell — show the notifications.
    "And he was told. These messages are not written by the booking code — a separate worker reads the record of what happened and turns it into messages. Which means a message that fails to send can never cause a booking to fail."
    1:55 — "Written by a separate worker, not by the booking code."
  8. Window 1Request an extension that fits. Then one too long. Then one blocked by the next booking. Hold 4 seconds on the refusal.
    "Extensions work the same way — checked against what is really free. Room to spare, granted in full. More than fits, so she gets the part that fits and is told why. And refused — because the next customer arrives in ten minutes, and their booking is a promise too. That last one is the one I would point at: it would be very easy to build a system that always says yes to the person standing in front of you."
    2:25 — "Refused — the next customer arrives in ten minutes. Their booking is a promise too."
  9. Open /admin/schedule-quality. Point at a sample size, then at a "no data" tile.
    "Two of these invite a wrong reading, so let me define them. Utilization is the share of the capacity we published, not of the whole day — it does not collapse just because a station is shut overnight. And preference match counts a slot within tolerance of the time someone asked for, not an exact hit on the minute. Both are the honest measure rather than the flattering one."
    "And every number here has moved. Thirty-one measurements — how full the chargers are, how often drivers get the time they asked for, how many waitlisted drivers we eventually serve, how much time comes back from early departures. Notice each one shows how many cases it is based on, because a percentage over three events is not a trend. And where we have no data it says 'no data', never zero. A zero looks like a real measurement, and would quietly mislead the person reading it."
    2:50 — "'No data' — never zero. A zero looks like a measurement."

EDIT

Editing and playback

What to add afterwards, and how to run it on the day.
RuleWhy
Record with no voice at allYou narrate live. A recorded voice under a live one is unlistenable, and it locks your timing.
Add only the amber overlays listed aboveEach one marks a decision the screen does not show. Everything else is noise.
Keep each overlay on screen 4–5 secondsLong enough to read twice. Any less and the audience is still reading when it goes.
Cut every waitThe workers run on a one-minute loop. Cut it and caption "60 seconds later" — honest, and it saves a minute of dead air.
Hold where the script says holdThose pauses are where you will be talking. Without them you will be narrating over a screen that has already moved on.
Export 1080p, no musicMusic competes with a live speaker.
On the day: the person who recorded a video is the person who talks over it. Start it, then narrate from your green boxes. If you fall behind the picture, stop narrating and let it play — the overlays carry the meaning on their own. Pick the thread back up at the next beat.
